# Архитектура доступа: Prometheus + Grafana на VPS

## Почему не всё дома

Экспортер **обязан** оставаться в домашней сети, рядом с устройством — он общается
с ним по локальному протоколу Tuya, который физически не выходит за пределы одной
локальной сети. Cм. `router/README.md`.

А вот **Prometheus и Grafana** можно разместить где угодно, лишь бы был сетевой
доступ до эндпоинта экспортера.

## Схема

```
Телефон/ноутбук → VPN-клиент (X-UI/Xray, TUN-режим) → VPS
                                                          │
                                                          │ (Xray routing: подсеть
                                                          │  туннеля → direct)
                                                          ▼
                                                    WireGuard-туннель
                                                          │
                                                          ▼
Роутер (экспортер + WireGuard-клиент) ── LAN ── устройство (пылесос и т.д.)
```

Без VPN — адрес VPS внутри туннеля недостижим извне вообще (это приватный IP,
не существующий в публичном интернете вне туннеля). С VPN — трафик идёт через VPS,
у которого есть прямой доступ к этой подсети.

## Компоненты

### 1. Роутер — экспортер + WireGuard-клиент

Многие домашние роутеры на Linux поддерживают WireGuard-клиент нативно, без
дополнительных пакетов — это отдельная функция от Entware/OPKG, которым ставился
Python для экспортера (см. `router/README.md`).

Роутер сам генерирует пару ключей и инициирует **исходящее** соединение к VPS — это
работает даже если домашний интернет за **CGNAT** (провайдер не выдаёт настоящий
публичный IP, из-за чего классический проброс портов в обратную сторону невозможен
в принципе, а исходящие соединения проходят всегда).

При настройке подключения на роутере:
- **Allowed IPs** — указывай **только** адрес VPS внутри туннеля (например,
  `10.0.0.1/32`), **не** `0.0.0.0/0` — нам нужен только туннель к VPS, не весь
  интернет-трафик через него.
- **НЕ включай** опцию вида "Использовать для выхода в интернет".

### 2. WireGuard-туннель (роутер → VPS)

Пример адресации (замени на свою собственную приватную подсеть):
- VPS: `x.x.x.x/24`, слушает `51820/UDP`
- Роутер: `x.x.x.x/24`

Конфиг на стороне VPS — `/etc/wireguard/wg0.conf`, добавь пира для роутера отдельной
секцией `[Peer]`.

### 3. Firewall на роутере — два обязательных правила

Без них связь либо не заработает, либо откроет обход VPN:

- **Разрешающее правило** для самого WireGuard-соединения (в разделе "Межсетевой
  экран", создать правило для этого подключения) — иначе роутер по умолчанию
  блокирует входящий трафик на новых VPN-интерфейсах, и туннель поднимется
  (handshake пройдёт), но реальные пакеты (ping, HTTP) ходить не будут.
- **Запрещающее правило** на вкладке "Домашняя сеть" (или "Основной" — так может
  называться этот сегмент в интерфейсе), блокирующее доступ **из** домашней сети
  **в** подсеть туннеля (например, `10.0.0.0/24`). Без этого правила роутер, как
  обычный маршрутизатор, будет прозрачно пропускать трафик из домашнего Wi-Fi прямо
  в туннель — то есть развёрнутые ресурсы окажутся доступны с любого устройства
  в домашней сети, без VPN вообще.

### 4. Grafana на VPS

Может показаться логичным привязать Grafana к `127.0.0.1` на VPS и разрешить доступ
к нему через Xray (добавив исключение из блокировки приватных адресов в
routing-конфиге). **На практике это не работает** — большинство VPN-клиентов на
базе TUN-режима **не заворачивают трафик, адресованный на `127.0.0.1`, в туннель
вообще**. Это особенность работы сетевого стека почти всех ОС: loopback-адрес
обрабатывается ядром устройства специально, в обход обычной маршрутизации, и
туннель физически не может его "перехватить" — попытка подключиться к
`127.0.0.1` с телефона обращается к **самому телефону**, а не к VPS.

**Рабочее решение** — привязать Grafana не к loopback-адресу, а к **собственному
адресу VPS внутри WireGuard-туннеля** (например, `10.0.0.1`, тот же, что назначен
интерфейсу `wg0` на VPS). В этом проекте это уже вынесено в переменную окружения
(`GRAFANA_BIND_ADDR` в `.env`, см. `.env.example`), которую Docker Compose
подставляет в `docker-compose.yml`:

```yaml
ports:
  - "${GRAFANA_BIND_ADDR}:3000:3000"
```

Это уже обычный приватный IP, а не специальный loopback — туннель прекрасно его
маршрутизирует. Заходить нужно на `http://<GRAFANA_BIND_ADDR>:3000` (не `127.0.0.1`).

Дополнительно нужно правило маршрутизации в Xray на VPS, разрешающее доступ именно
к этой подсети (обычно такие приватные диапазоны блокируются по умолчанию как защита
от SSRF-атак) — добавляется в `routing.rules` **выше** правила блокировки
`geoip:private`:

```json
{
  "type": "field",
  "ip": ["x.x.x.x/24"],
  "outboundTag": "direct"
}
```

### 5. Docker и `ufw`

Если помимо привязки к конкретному IP захочется подстраховаться через `ufw` —
учти, что Docker управляет `iptables` напрямую и может **обходить** правила `ufw`
для портов, опубликованных через `docker-compose` (`ports:`). Привязка порта к
конкретному IP (как выше, `10.0.0.1:3000:3000` вместо `0.0.0.0:3000:3000` или
просто `3000:3000`) — надёжнее, чем полагаться только на `ufw deny`.

## Диагностика

1. Проверь связность туннеля независимо от остального: `wg show` на VPS — должна
   быть свежая `latest handshake` для пира роутера.
2. Проверь доступность самого экспортера через туннель — с VPS:
   ```
   curl http://x.x.x.x:9099/metrics
   ```
   Должны прийти метрики в текстовом виде.
3. Проверь Prometheus — на VPS (или через временный SSH-туннель):
   ```
   curl -s http://localhost:9090/api/v1/targets
   ```
   Таргет должен быть `"health":"up"`.
4. Проверь фаервол VPS/роутера пошагово, а не всё сразу — так проще понять, на каком
   именно шаге что-то не работает.

## На будущее

- Если IP роутера в домашней сети (для внутренних правил) или сама модель роутера
  сменится — WireGuard-подключение и оба firewall-правила нужно настраивать заново.
- Если VPS сменится/переустановится — WireGuard-конфиг на обеих сторонах нужно
  пересоздать.
